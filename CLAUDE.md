# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A clickable prototype of the HAU-SOC Thesis & Capstone workflow system (React 18 + Vite 5, plain JS/JSX, no TypeScript). Its job is to make the **workflow and its Context-Aware Access Control (CAAC)** testable end to end: sign in as any persona, push a project through the life cycle, and watch permissions, worklists, emails (dev outbox) and the audit trail respond.

## Commands

```bash
npm install
npm run dev        # http://localhost:5180 (port pinned in vite.config.js)
npm test           # Vitest: guard tests for §7 T1–T21 + service/write-path tests (src/__tests__)
npm run test:rules # storage.rules + claims sync against the running emulators (docker compose up); restores the open rules after
npm run test:triggers # claims triggers live on the Functions emulator, in a throwaway container (fresh data)
npm run test:act   # writes through `act` end to end under the REAL rules: seed, real Auth accounts, browser SDK (throwaway container)
npm run build:functions # bundle src/services for the `act` function → functions/lib/app.js (gitignored; firebase.json predeploy runs it)
npm run build
npm run preview
node scripts/dummy-docs/generate.mjs   # dummy manuscripts, forms and certificates → test-fixtures/dummy-documents (needs Chrome; macOS for TOC page numbers)
node scripts/pwa-icons/generate.mjs     # re-render public/ PWA icons from scripts/pwa-icons/icon.svg (needs Chrome)
```

The pane's Mobile preset emulates touch; its Tablet preset does not, so it behaves like a narrow desktop window (editing allowed).

Once push is configured the open-app path stands down. Same tag (outbox id) on both, so each shows once. A notification never carries the email's text — only a general line (`src/deviceNotice.js`, copied in `functions/index.js`; Figma PWA-12). The account menu's switch (Figma PWA-09–11) turns them off per account per device (`hausoc.notify.off.<userId>`, push token dropped); phones and tablets get an install banner on the dashboard (`hausoc.install.dismissed`) and a step sheet per browser (`components/Pwa.jsx`, Figma PWA-01–07). `public/sw-notify.js` handles push and taps. Still no in-app notification list. Per-browser rules (iOS Home Screen only from 16.4, in-app browsers, Android install menus) live in `src/browserSupport.js`, pure functions tested from real user-agent strings in `browserSupport.test.js`; the open app stands down for push only after this device registered (`hausoc.push.device`), so browsers where push signup fails (e.g. Brave) still get notifications.

- **`.env` may point at the live Firebase project** (`VITE_BACKEND=firebase`). Vite and Vitest both load it. Tests are pinned to the local backend (`vite.config.js` `test.env`, `backend/index.js`); for browser checks use the `capstone-prototype-local` launch config (port 5181, `VITE_BACKEND=local`). Dev-tools resets refuse to run against a live project.
- No linter or formatter is configured. Beyond `npm test`, verify by running the app and walking the §7 scenarios in `docs/WORKFLOWS.md` — **Dev tools → Load scenario T#** sets each one up.
- Default backend is `local` (in-memory, mirrored to `localStorage` key `hausoc.db.v13`); seed data (§6 personas, G1–G4) loads on first run and can be restored from **Dev tools → Reset seed** (dev builds only). If you change the seed or the store shape, bump the key or reset — stale browser data will otherwise mask the change.
- Firebase: `cp .env.example .env`, then `VITE_BACKEND=firebase npm run dev`. Against emulators: `firebase emulators:start` + `VITE_USE_EMULATORS=true VITE_BACKEND=firebase npm run dev`.
- Docker: `docker compose up` runs the Vite app (5180, hot reload via the bind mount) against the Firebase Emulator Suite (UI on 4000; Firestore 8080, Auth 9099, Storage 9199, Functions 5001), project `demo-local`; dependencies (root and `functions/`) are installed in the image and kept in the named volumes `node_modules` / `functions_node_modules`; `functions-build` (`scripts/functions/dev.sh`) reinstalls them when a `package.json` or lock changes (`scripts/docker/deps.sh`, hash stamp `node_modules/.docker-deps`), writes the placeholder `functions/.secret.local` on a fresh clone, then rebuilds the `act` bundle on every source change; the Functions emulator reloads it. `APP_WRITE_PATH=direct docker compose up` makes the browser write to the emulators itself instead. On the emulator `act` accepts the dev panel's persona (`as`, `FUNCTIONS_EMULATOR` only — personas are not Auth accounts) and `deliverOutbox` sends nothing (`functions/.secret.local` holds a placeholder key, gitignored); compose env overrides `.env`, so it never reaches the live project. The emulators load the open rules in `emulator/` (the real `firestore.rules` deny client writes); `FIREBASE_CONFIG=firebase.json` loads the real ones. Data persists in `.emulator-data/` (export on clean stop). Rebuild with `--build` after a Dockerfile change; `docker compose down -v` drops the dependency volumes. firebase-tools is pinned in `Dockerfile.emulators`. The browser reaches the emulators on the host that served the page (`src/backend/emulatorHost.js`; `localhost` → 127.0.0.1, `VITE_EMULATOR_HOST` overrides), so other PCs on the network can use one machine's stack. The stack needs nothing but Docker on the machine — no `.env`, Node or firebase CLI — and tolerates a CRLF (Windows) checkout.

## Workflow reference — source of truth

- `docs/WORKFLOWS.md` is the source of truth for roles, stages, permissions (CAAC) and cross-role behavior. Where the README's "Decisions the prototype had to make" or current code disagree with it, follow `WORKFLOWS.md`.
- **Every action must pass one guard** that checks the user's global role + their role on that project + the project stage (§2.2). Hiding a button is not enough — the service call must reject it too.
- Items marked **"Mockup default"** are placeholders, not team decisions. Each lives behind a named flag in `src/domain/flags.js` (with `FLAG_NOTES` saying where it is wired). Add new ones there rather than scattering constants.
- **Never build anything listed in §9** (obsolete / out of scope) — students drafting their own groups was removed from that list on 2026-10-30 (flag `STUDENT_GROUP_DRAFTS`, `components/GroupDraft.jsx`): e.g. OTP, public gallery, grading/rubrics, chat, Kanban, in-app editing, video uploads, `EVALUATION_FORM` screens.
- **Seeded accounts are never emailed.** Every seed persona and NPC carries `demo: true`; their addresses are on the real `@hau.edu.ph` / `@student.hau.edu.ph` domains and may belong to real people. `deliverOutbox` (`functions/mailRouting.js`) sends their mail to `MAIL_REDIRECT_TO` (functions/.env) instead, with the original recipients in the subject, or not at all when it is unset; real accounts are mailed as written. Keep `demo: true` on any account you add to the seed.
- The seed (`src/backend/seed.js`) uses the **§6 test personas** (Prof. Alpha … Admin Sierra, plus Prof. Foxtrot as G3's Panel Chair and Prof. Papa awaiting activation), groups G1–G4 and one ungrouped student. `src/backend/npcs.js` adds NPC students and faculty (`npc: true`) so every program has **three groups of four** (flag `GROUP_SIZE`): G1–G4 are topped up, and NW, EMC, CYB and CS get the rest. No §7 scenario depends on an NPC; tests that list a group's members read them from the store. `src/backend/stageBuilder.js` puts any project at any stage with plausible prerequisite data; the seed and the dev tools both use it.
- `docs/ROLE_TEST_PROMPTS.md` holds the per-role test prompts; reports go to `test-reports/`.
- Per-stage polishing follows the five checks in §1 (actor screen, CAAC guard, state change, reflection on other roles' screens, side effects) and the prompt template in §10.

## Architecture

The workflow and the permission model are **data**; the UI renders from them.

**`src/domain/caac.js` — permissions.** No role carries a permission on its own. Each policy is `role × capability × context condition` (`g(...)` for Global Roles, `p(...)` for Project-Based Roles). Conditions are composable (`at(stage…)`, `from(stage)`, `during(phase…)`, `member`, `inScope`, `notTheAdviser`, `all(...)`) and self-describing, so denials explain which condition failed.
- `resolveContext(user, bundle)` → `{ grants, active, dormant, projectRoles, … }` for one user on one project at its current stage. `resolveInstitution(user, snap)` does the same for non-project capabilities (group creation, reports, admin). Inactive or unverified accounts resolve to no grants.
- `document.read` is separate from `project.view`: the System Administrator opens project records (§2.2) but never documents.
- **Permission overrides** (flag `PERMISSION_OVERRIDES = 'deny-only'`, collection `permissionOverrides`): `evaluate()` drops a revoked capability into `dormant` with the override as the reason. An override can only remove a grant, never add one. Bundles carry `overrides` (this project + `projectId: null`).
- Admin-editable settings live in `settings/global`, read through `src/domain/settings.js` (e.g. `revisionDaysOf(snap)`, falling back to the flag).

**`src/domain/guard.js` — the one guard (§2.2).** `canView(user, bundle)` and `canDo(user, action, bundle, target)`; `ACTIONS` maps every action name (plus one per stage gate) to its capability and allowed document/log states; `allowedActions(hat, stage, docState)` generates the role hat × stage table. `viewBundle(user, bundle)` is the read-side filter — the UI renders from it, never from a raw bundle (latest-version-only for the panel, private notes per `canViewAnnotation`, AI summary per audience).
- `allowedDocTypes(stage)` controls which uploads each stage accepts.
- UI code checks **capabilities**, never role names.

**`src/domain/stages.js` — the stage machine.** `STAGES` is an ordered list; each stage declares `gates` with `{ action, capability, next, requires(bundle), handledIn?, signs?, done? }`. `next` may be a function (e.g. re-defense loops back to scheduling), or `null` for a gate that records its effect without moving the stage (S3.4 title registration); `done(bundle)` drops a completed gate from `openGates()`. `handledIn` gates run from a tab, not `runGate` (e.g. `APPROVE_CONCEPT_PAPER` fires when Instructor 1 approves the concept paper in `submitReview`). Timeline, worklist, "Next step" panel and blocked-step messages all derive from this file. Changing process order or a gate's precondition should be a change here, not in components.

**`src/services/` — the write path.** Every state change in `actions.js` follows: `authorizeOn(actor, projectId, action, target)` (reads the signed-in session and the store fresh — the `snap` components pass is ignored) → `perform(key, fn)` (in-flight dedupe + `db.transaction`, all-or-nothing) → `logAudit({ actorId, hat, before, after })` + `logHistory` → `notify` (email only — mock email in the `outbox` collection; there is no in-app notification inbox, by team decision). Stage moves go through `transition()`, which writes `workflowHistory` and notifies whoever holds the next gate's capability (resolved through CAAC, not a fixed role list). `runGate()` is the generic gate executor; gate-specific side effects are branches on `gate.action`. `core.js` builds the per-project **bundle** (project + members, assignments, documents, reviews, defenses, forms, history…) that both CAAC and stage guards consume. `worklist.js` computes "what each user owes right now" purely from CAAC + bundle.

**Writes in the Firebase build go through the `act` Cloud Function** — when `VITE_WRITE_PATH` is `functions` (`writePathOf` in `remote.js`; unset: `functions` on the emulators, `direct` on a live project until `act` is deployed; the rail shows which). `direct` is the explicit fallback: the browser writes to Firestore itself, which only the emulators' open rules (or a live project with open rules) accept, and the guard then runs in the browser only. There is no automatic fallback — an unreachable `act` fails the call. Components import service calls from `services/api.js`, never `actions.js`: locally it *is* `actions.js`; in the Firebase build each call listed in `services/remote.js` is sent to `act` as `{ name, args }` (the actor and `snap` are never sent; args travel as plain JSON, so a gate object's functions drop out — the server re-reads gates from `stages.js`). `act` runs the same `actions.js`, bundled by `scripts/functions/build.mjs` (browser-only modules swapped: `functions/app/backend.js`, `stubs/`), as the caller the ID token names (`token.userId`; registration and email confirmation are matched by the token's email): `functions/app/store.js` reads every collection except `auditLogs`/`outbox` inside one Firestore transaction, runs the action in memory and commits what changed — concurrent requests retry rather than act on stale data (`concurrency: 1` per instance; the session and snapshot are module state). Refusals keep the service's message (`AccessDenied` → `permission-denied`, others → `failed-precondition`; programming errors → `internal`, logged). A submission's PDF is still uploaded by the browser (after `checkSubmission`, so a refused submission uploads nothing); `act` gets its `storagePath` and `functions/app/files.js` verifies the object (project, type, uploader, real PDF ≤ 25 MB, bytes match the recorded `sha256`) before recording it. On the server the AI summary keeps its placeholder sections (no text extraction or Gemini key there yet). The overdue check runs hourly (`overdueRevisions`). Only the dev tools' resets still write directly, on the emulators.

**`src/backend/` — swappable repository.** `index.js` picks `localAdapter` or `firebaseAdapter` from `VITE_BACKEND`; both expose the same surface (`subscribe`, `add`, `update`, `get`, `replaceAll`, …). Services and components must go through `db`, never Firestore directly. `schema.js` lists collections and documents the manuscript-ERD → collection mapping. `files.js` keeps submitted PDF bytes (IndexedDB locally, Cloud Storage + `storage.rules` on Firebase), write-once per version: resumable upload with progress/cancel, store errors mapped to plain messages, reads through `getBlob` (never download-token URLs, which bypass the rules — the live bucket needs `storage.cors.json` applied once: `gcloud storage buckets update gs://<bucket> --cors-file=storage.cors.json`); `sampleFiles.js` pairs seeded documents, which have no bytes, with the dummy PDFs in `test-fixtures/`. `submitDocument` takes the `File` itself (never caller-supplied name/size/type): `domain/uploads.js` (`pdfProblem`, `inspectPdf`, shared with the upload form) checks it is a real, non-empty PDF ≤ 25 MB and fingerprints it (`sha256` on the record and on the object's metadata); the byte check and upload run as `perform()`'s `prepare` step, under the in-flight key, so a double-click uploads once. `authService.js` (registration/login/email verification) and `call()` in `services/push.js` (callable Cloud Functions) are the only other Firebase touchpoints; a single document outside the mirrored collections is read with `db.watch()` (e.g. `claimsSync` in `services/claims.js`).

**`src/state/AppContext.jsx`** subscribes to the adapter and exposes the whole snapshot (`snap`, arrays per collection), the signed-in user `me`, and demo controls. Components call service functions with `(me, snap, …)`; `components/useAction.jsx` wraps calls so guard errors surface inline instead of throwing.

**Dev tools (R9).** `src/dev/` — the sign-in **demo panel** (`DemoPanel.jsx`: personas grouped by project cast, by role, and §7 scenarios by project; picking someone signs in straight onto the tab where their next step is, from `worklistRow`), the rail persona switcher, `/dev` page (scenario loader T1–T21, set stage, reset, overdue job, outbox, audit/history viewer, flags, allowedActions). Loaded only behind `import.meta.env.DEV`, so production builds drop it.

**Annotations.** `components/ManuscriptViewer.jsx` renders the PDF with pdf.js (legacy build, lazy-loaded) and draws annotations as an overlay; reviewers select words or drag an area. Positions are page fractions (`domain/annotations.js`), so the file is never written to; `addAnnotation` validates them.

**"Acting as" contexts (Figma F02, 01 · Dashboards).** `src/domain/workspaces.js` lists the 11 contexts (each Global Role, each Project-Based Role across its groups, and the group member) with their rail (`nav`); `contextsOf(user, snap)` gives the ones an account holds. `components/Workspace.jsx` keeps the selected one (`localStorage` `hausoc.context.<userId>`; with none saved, the role behind the first thing owed) and the worklist rows in it. The top-bar switcher changes the rail and `pages/Dashboard.jsx` picks the desk (`pages/dashboards/`); the rail's pages are `pages/WorkViews.jsx`. Presentation only — the guard is unchanged. A new rail entry needs its route in `App.jsx` (`workspaces.test.js` checks).

**UI.** `pages/ProjectWorkspace.jsx` hosts the tab panels in `components/panels/` plus the `CaacInspector` (shows active vs dormant grants per role for the current project/stage). Styling is a single `src/styles.css` with CSS variables.

## Invariants to preserve

- Documents are immutable: a new upload is a new `versionNumber`; the previous one becomes `Superseded`. Never overwrite.
- Audit log is append-only.
- Panel roles see only the latest document version; private panel annotations stay hidden until the Panel Chair records the verdict.
- Forms (FM-AAC-SOC-2004, FM-AAC-SOC-2005, Approval Sheet) are signed in the order defined in `src/domain/forms.js` — **outside the system** (revision 2026-10-30): each 'upload' line takes the signatory's signed copy (PDF/JPG/PNG, `uploadFormFile` → `projects/{id}/forms/…`, `form.copies`), each 'confirm' line is recorded in the system (`lineMethod`). Weekly logs (FM-AAC-SOC-2003) are uploaded files the Adviser marks reviewed. Blank templates: `test-fixtures/dummy-documents/blank-forms/` (`components/FormFiles.jsx`, page `/forms`).
- **Custom claims** (`functions/claims.js` builds, `syncClaims.js` writes; triggers in `functions/index.js` on `users`, `projectMembers`, `projectAssignments`, `permissionOverrides` and Auth sign-up, plus the `refreshClaims` callable): `userId` (the `users` id — not the Auth uid; the two are linked by email, so rules compare record owners with `me()`, never `request.auth.uid`), `globalRoles`, `programScope`, `projects` `{ id: [roles] }`, `hidden` (an override revoking project.view/document.read everywhere). Mirrors `resolveContext` (`claims.test.js` checks every seeded account); claims over 1000 bytes drop archived projects first. After a change `claimsSync/{uid}` is touched and `src/services/claims.js` refreshes the ID token.
- `firestore.rules` mirrors the `project.view` policies in `caac.js` — keep them in step when changing visibility. `storage.rules` copies `allowedDocTypes()` (PDF types per stage, `pdfTypesAt`); `storageRules.test.js` fails when they drift.
- Registration is restricted to `@hau.edu.ph` / `@student.hau.edu.ph` (`EMAIL_DOMAINS` in `constants.js`).
